An agent finds a planted bug in tududi

An agent gets a bug report for tududi, an open-source task manager: “I click Plan your day and my high-priority task comes last.” It clicks the link itself, reads the trace and fixes the sort.

Why your agent needs it

Without it

Your agent reads a bug report and can only read code. It picks where to look from file names and text search. When that runs out, it asks you to click the button and paste what you see.

With Lightpath MCP

  • The agent clicks the button itself, in a browser Lightpath opens.
  • It gets back the functions and lines that ran, in the browser and on your Node server, and the lines inside them that didn’t.
  • Errors and failed requests come in the same answer.
  • After a fix, it clicks again and compares the two traces.

Lines come from V8’s own coverage counters, so they show what ran, not what the code seems to do.

What your agent gets back

Part of the real answer from the tududi run above, cut where it says “…”. Each line is a function that ran: its name, its line numbers, and how many times it ran. The dots show the count. After “not run” come the lines inside it that didn’t run.

How it works

  1. {{SPOT1}}

    The agent clicks

    run_action clicks a button or link in the Chromium browser Lightpath opened for your app. It can fill form fields first.

  2. {{SPOT2}}

    V8 records what ran

    Lightpath reads V8’s coverage just before and after the click: in the browser over the DevTools Protocol, and in your Node server through a small preloaded agent. Requests from the click carry a header that joins the two.

  3. {{SPOT3}}

    Your agent gets the trace

    Source maps turn the byte ranges into your own files and lines. The answer goes to your agent over MCP, cut to fit 16,000 characters.

What it does

run_action: click and trace in one call

The agent names a button or link the way a person would. Lightpath clicks it and returns that click’s trace. You don’t click or paste anything.

run_action  target: button "Mark as paid"  within: "Kestrel Labs"

request: POST /api/invoices/INV-2041/pay → 200 (node, 4 ms)
…
  server/services/ledger.ts
    getSummary 14-28 ×1 not run: 16-27
…

Tested in scripts/e2e-shop.mjs. Excerpt from a recorded run on examples/invoices.

Errors come with the trace

A thrown error and failed requests, like a 409 or a 400, show up in the same answer as the code that ran. Lines after a call that threw read unknown, never run: V8 has no count for them.

D-121, D-153, tested in scripts/e2e-shop.mjs and pnpm accuracy.

Check a fix in one call

After a fix, the agent runs the same click with compareTo: "last". The answer adds what ran in only one of the two traces: functions, not-run lines and request status.

D-118, D-144, tested in scripts/e2e-invoices-fix.mjs.

run_request for API backends

One HTTP request to your app on localhost, no browser. You get the backend lines it ran. Loopback only: it refuses other hosts, redirects and proxies.

D-125, 18 cases in packages/mcp/test/request.test.ts, scripts/e2e-api.mjs on 7 backend apps.

One command to set up

For Claude Code, Cursor, VS Code or Kiro. It writes the agent’s MCP config, a lightpath.config.json and a short note in AGENTS.md on when to use Lightpath.

CI runs all four on Linux, macOS and Windows: scripts/setup-check.mjs.

Stays on your machine

The daemon listens on 127.0.0.1 and needs a token. Lightpath sends no data off your machine. Secrets in URLs, tokens and key=value pairs become [redacted], and request and response bodies are never collected.

D-123, packages/daemon/test/server.test.ts, packages/mcp/test/redact.test.ts.

Quick start

In your app’s folder: a React frontend, a Node server and a dev script in package.json. You need Node.js 22.12 or newer and Chrome or Edge.

Not yet

  • Chromium browsers only (Chrome or Edge).
  • No socket.io or WebSocket messages, Web Workers or Next.js server components.
  • No Python backends in click traces yet; a Python agent is in preview.
  • run_action clicks and presses Enter or Space. No hover, drag, file upload, dialogs, popups or iframes.

Next, in this order: Next.js, socket.io, then Python (FastAPI).
